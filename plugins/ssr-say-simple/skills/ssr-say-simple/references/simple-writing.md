# 写清楚，再选择展示方式

本指南借鉴简明技术写作原则，不是 ASD-STE100 的中文翻译或合规实现。

## 表达

- 先写用户可观察的结果，再解释原因与实现。需要时用「谁 → 条件 → 动作 → 结果」检查是否说清楚，不要求每句套模板。
- 一句讲一个重点，一段讲一个主题。用常用词、明确的主语和具体动作。同一事物保持同一个名称；必要术语首次出现时解释。
- 保留数字、单位、条件、例外、否定、概率和责任程度。「建议」不等于「必须」，「可能」不等于「能够」；不为缩短句子删掉这些区别。
- 原始引文、代码标识符、API、文件路径不做措辞替换。改写的内容必须标为摘要或解释，不冒充原话。
- 区分事实、推断、待验证事项和拟议方案。概念图或界面草图不能作为已经实现的证据。

例如：

> 模糊：通过异步机制赋能订单处理体验。
>
> 清楚：店员接单后，顾客页面显示「商家已接单」。同步失败时，页面保留原状态并提示重试。

## 根据读者要判断的问题选组件

| 问题 | 展示方式 | 阅读后应能判断 |
|---|---|---|
| 界面改在哪里？ | `doc-shot` 现状 + `doc-mock` 草图 | 信息、位置和操作的区别 |
| 谁先做什么？ | `doc-seq` 时序图 | 调用顺序和责任归属 |
| 数据往哪里走？ | `doc-flow` 流程图 | 输入、处理和输出 |
| 失败、重试后怎样？ | `doc-machine` 状态图 + 对应草图 | 每个状态的结果和下一步 |
| 两种方案怎么选？ | 对比表 + `doc-ask` + `data-if` | 相同条件下各自的收益、代价和限制 |
| 实现依据是什么？ | `doc-code` / `doc-calls` | 真实入口、代码与拟议改动 |

先给最小的有效展示。一张图回答一个问题，不要求每页凑齐组件。没有复杂关系时，短段落或表格就够了。

## 让选择的后果可见

先展示共同前提，再给选项。用 `data-if="decision=value"` 让界面草图、说明或状态演示与选项一致。切换选项不能只改变单选框，却留下互相矛盾的图。

以 `examples/retry-explainer-zh.html` 为可运行参考：自动重试与手动重试有各自的状态图，读者点击状态能看到对应提示。这里的状态切换只演示方案，不发送真实请求。

保留原有批注与反馈机制。预选项仅是建议；用户没看过的默认项不是批准。反馈可以要求解释或修改方案，不必直接进入实施。

## 检查边界

打包器对中文/中英混排计数：每个汉字算一个单位，非汉字单词或数字算一个单位。句子超过 50、段落超过 150 单位时提示；英文参考阈值分别为 25 和 40 词。这些是便于复查的启发式阈值，不是合格分数。

检查器跳过引文、代码和图的脚本源。它不能证明术语始终一致、意思没有改变、事实正确或方案可实现；交付前仍需对照原需求检查。它只报告，不自动改写。

不制作视频，不调用语音服务。交互式演示应能手动操作，无需自动播放动画。
